# BUG20260902: one-PSD spectrogram dropout after trigger ON

## Symptom

In recorded Meteoris event spectrograms, the meteor signal could sometimes drop
to the noise level for exactly one PSD row shortly after the detector ON
transition, often about 2-3 PSDs after ON, then resume normally.

The issue was intermittent and was most visible in triggered recordings because
the event start is the moment when Meteoris writes both the pre-trigger context
and the first active PSD row.

## Root cause

The PSD callback ran detector and HDF5 recorder work synchronously while a
SoapySDR direct-access read buffer was still held.

With direct-buffer acquisition, Meteoris receives a pointer to a driver-owned
input buffer and must release it quickly with `releaseReadBuffer()`. Before the
fix, the flow was:

```text
acquire Soapy direct buffer
process input samples
generate PSD frame(s)
PSD callback runs detector
trigger ON writes pre-context backlog to HDF5
write current active PSD to HDF5
release Soapy direct buffer
```

Trigger ON is a bursty path because the recorder can write the entire
pre-trigger PSD backlog plus the first active frame. Holding the Soapy buffer
during that HDF5 work can starve the SDR direct-buffer ring on real hardware,
causing a short acquisition discontinuity. A single affected input interval can
appear as one PSD row at the noise floor in the output spectrogram.

## Solution

The main loop now separates PSD production from detector/HDF5 recording:

```text
acquire Soapy direct buffer
process input samples
generate PSD frame(s) into preallocated PSD ring slots
queue pointers to completed PSD slots
release Soapy direct buffer
run detector and HDF5 recorder on queued PSD frames
```

This keeps bursty trigger-time recorder work out of the direct-buffer hold
interval.

To avoid introducing a new allocation-heavy copy path, `WelchBandPsd` now owns
a preallocated circular ring of `PsdFrame` slots. Each slot's `powerDensity`
vector is sized once. The callback queues only `const PsdFrame *` values, and
the queued frames are consumed before the next SDR read is processed, so the
ring cannot overwrite live queued frames in normal operation.

The pre-trigger context in `PsdDetectorRecorder` was also changed from a
`std::deque<BufferedFrame>` to a pre-sized circular buffer. This keeps the
required pre-context PSD copies, but removes repeated deque growth and frame
allocation during steady idle operation.

The remaining PSD data copy is intentional: pre-trigger rows must survive until
a later trigger ON, so they cannot be stored only as references to the transient
PSD producer ring.

## Verification

The fix was validated with:

```bash
cmake --build build
./run_sim.sh --output-directory /tmp/meteoris_psd_ring_check \
  --run-seconds 12 \
  --log-file /tmp/meteoris_psd_ring_check/meteoris.log \
  --log-file-truncate
```

Results:

- build completed successfully;
- simulator run completed with `overflows=0`;
- HDF5 output contained 1060 recorded PSD rows with shape `(1060, 1639)`;
- recorded frame indexes and timestamps were monotonic;
- `git diff --check -- src/meteoris.cpp` passed.

The simulator also confirmed that detector/HDF5 work no longer runs inside the
Soapy direct-buffer hold interval. The measured post-FIR/PSD callback time over
a 12-second simulator run dropped from about 0.80 s in the synchronous callback
path to about 0.26-0.27 s with the ring-backed delayed recorder path.

## Subsequent hardening

Later trigger-latency instrumentation showed that releasing the direct buffer
before recording reduced the original failure probability but did not remove
the acquisition/storage coupling.  Ordinary trigger-ON pre-context writes were
observed to stall the main acquisition loop for roughly 45-55 ms while a new
131072-sample block arrived every 13.107 ms at 10 Msps.  The SDR driver normally
buffered those blocks successfully, but correctness still depended on driver
queue depth and the long-tail latency of HDF5/filesystem operations.

Meteoris therefore now uses a dedicated recorder thread.  Completed PSD frames
are copied by the acquisition thread into a bounded, preallocated ring.  The
recorder thread owns detector/event state, pre-trigger context, HDF5 appends,
compression and SWMR flushing.  Acquisition/DSP no longer waits for storage
latency.

The recorder queue is sized for roughly eight seconds of PSD data (with fixed
minimum and maximum frame bounds).  It is intentionally bounded: if the writer
ever falls behind far enough to exhaust the queue, Meteoris logs an explicit
queue-overrun error and stops instead of silently losing PSD rows.  Normal
shutdown drains all queued frames before the HDF5 writer is closed.
